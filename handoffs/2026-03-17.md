# LongMemEval Handoff - 2026-03-17

## Scope

This work session focused on the Batch 0 LongMemEval v1 runner under `evaluation/longmemeval/`, plus follow-up debugging of retrieval and answer-generation failures.

Two goals were active:
- Keep a defensible, benchmark-clean evaluation path for leaderboard placement.
- Keep a more aggressive development path available for reducing false positives during iteration.

## Main Outcome

The eval stack now supports two answer-generation profiles:
- `clean` (default): intended for benchmark-clean runs.
- `dev`: intended for debugging and reducing scorer false negatives.

CLI usage:

```bash
npx tsx evaluation/longmemeval/src/runner.ts eval --batch 0 --question-ids id1,id2
npx tsx evaluation/longmemeval/src/runner.ts eval --batch 0 --question-ids id1,id2 --answer-profile clean
npx tsx evaluation/longmemeval/src/runner.ts eval --batch 0 --question-ids id1,id2 --answer-profile dev
```

The selected profile is written to:
- `run-manifest.json` as `config.answer_profile`
- each debug file as `answering.answer_profile`

## Clean vs Dev Profiles

### `clean` profile

Intended use:
- leaderboard / benchmark reporting

Keeps:
- broad evidence formatting improvements
- question-text-based guidance
- explicit-name extraction guidance
- explicit-duration-over-date-arithmetic guidance
- timestamp-aware ordering

Avoids:
- narrow score-chasing heuristics
- stronger tuned recommendation synthesis wording

### `dev` profile

Intended use:
- reducing false positives while iterating
- debugging scorer brittleness

Adds on top of `clean`:
- narrow lexical evidence boost for the `fruit` clue case
- stronger recommendation synthesis wording
- more score-friendly yes/no formatting guidance

Important:
- `dev` should not be treated as the clean headline benchmark score.

## Benchmark-Clean Judgment

The following are considered fair for a clean benchmark run:
- retrieval time-anchor fix
- time-window read from `memory_eval`
- deduping retrieved memories
- better evidence formatting
- question-text-derived guidance
- explicit-name and explicit-duration guidance

The following are considered borderline / tuned and should stay in `dev` only:
- narrow `fruit -> mango|fruit|fruity` evidence boost
- stronger recommendation synthesis wording aimed at scorer alignment
- exact `Yes.` / `No.` formatting guidance for yes/no questions
